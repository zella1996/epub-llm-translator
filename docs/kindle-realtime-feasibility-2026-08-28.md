# Kindle 实时调用 LLM：可行性研究

调研日期：2026-08-28。目标设备：此前记录的 Kindle Paperwhite 12 代；具体固件、
型号变体及是否已越狱尚未确认。本文是技术研究，不是实机验收或改造授权。
没有安装插件、修改设备、启动服务或调用付费模型，不改变
[现有实施方案](reading-assistance-implementation-plan.md)的离线首版范围。

## 结论

**在 Kindle 上按需调用模型有可行路线；在未越狱的原生书页内，自定义选中菜单并
动态填充模型答案，没有找到公开支持的实现接口。** 必须区分电子书渲染器、Kindle
浏览器和 KOReader 三种运行环境。

| 路线 | 能力与证据 | 本项目成本判断 | 主要边界 |
| --- | --- | --- | --- |
| EPUB 内嵌脚本调用 API | Amazon 转换规范明确移除脚本，不能作为受支持方案 | 不投入 | 浏览器支持脚本不代表书页支持 |
| 原生书内链接 → 浏览器 → 自建服务 | 外链有官方依据；本机完整往返尚待测试 | 概念验证低；可靠服务中等 | 固定段落入口，离开书页，不能直接获得任意选区 |
| 越狱 + KOReader + AI 插件 | 已有选区调用、解释与自定义 prompt 的开源实现 | 定制代码较少；设备和插件维护成本较高 | 取决于型号/固件，改用 KOReader 阅读 |
| Amazon Ask this Book | 有官方产品，但本次找到的最新公告仍限定美国 iOS | 不能视为本项目接入层 | 没有公开的自选 GLM 或个人 EPUB 接入说明 |

成本为相对工程判断，不是已测工期、速度或费用。实时也不等于即时：联网恢复、
服务排队、推理、屏幕刷新和回到原文都计入阅读中断时间。

## 1. 不越狱：外部浏览器可以研究，书内动态弹窗不应承诺

Amazon《Kindle Publishing Guidelines》2026.2 的 §6.3 明确：转换时会剥离脚本。
因此不能给 EPUB 添加 `fetch()`，期待转换后的原生书页像网页一样调用模型。
这是官方出版转换链路的约束，不是对所有非官方格式和固件漏洞的穷尽判断。
参见 [Amazon 出版规范](https://kindlegen.s3.amazonaws.com/AmazonKindlePublishingGuidelines.pdf)。

Amazon [超链接规范](https://kdp.amazon.com/en_US/help/topic/GQ6JQ7FM6C72HE4X)
允许与书籍相关的外部链接，但电子墨水设备上的固定版式书不支持这类链接。
旧版 [Kindle 用户指南，第 6 章](https://kindle.s3.amazonaws.com/Kindle_Users_Guide_5th_Edition.pdf)
明确描述从阅读材料的链接进入浏览器。旧指南不能代替当前 Paperwhite 的实机测试，
尤其不能保证发送转换后外链保留、HTTPS 登录、返回位置和休眠恢复均正常。

可验证的交互是：

```mermaid
flowchart LR
    A[原书段末：在线解释] --> B[Kindle 浏览器：对应段落]
    B --> C[明确点击生成]
    C --> D[服务端调用 GLM 并缓存]
    D --> E[浏览器显示短答案]
    E --> F[通过设备操作返回原书：待实测]
```

入口只能传入事先绑定的段落身份，不能自动传递原生阅读器当前任意选中的词句。
如需指定一句，可在网页中提供句子按钮，代价是多一次操作。答案显示在浏览器，
不会自动填入 Kindle 脚注、写回已经发送的电子书，或自动变成书内笔记。

本项目已验证的是**书内单向链接 → 章末辅助区 → 阅读历史返回**，见
[Paperwhite 实机记录](../COMPATIBILITY.md#paperwhite-手动验收产物)。这不能证明
跨浏览器的返回体验相同。此前弹窗吞内容的问题属于原生书页，也不能据此否定
KOReader 自己绘制的模型对话框。

### 若浏览器往返通过，服务端需要什么

- 复用 `ParagraphRef` 的章节/段落定位，增加书籍版本与原文 hash；URL 使用不含
  正文、书名或供应商密钥的随机标识。随机标识不能代替鉴权。
- 服务端保存对应段落；是否上传到云端需另行选择。只向模型发送用户请求的文本
  和明确允许的有限语境，不因一次点击自动上传整本书。
- 先用简单 HTML 与普通表单，提交后显示任务状态；保留手动刷新，不将流式 JS、
  WebSocket 或复杂前端框架作为设备兼容前提。
- 打开 GET 链接只读取已有结果或显示生成按钮，不立即产生付费调用；生成请求需
  鉴权、CSRF 防护和任务去重。刷新、连点、超时重试不能重复创建同一任务。
- 缓存身份覆盖原文、语境、请求类型、prompt 和实际模型设置；增加费用限额、
  超时、取消及并发控制。供应商密钥只留服务端，日志不记密钥或会话凭据。

本地电脑/NAS 部署需要持续运行且可被 Kindle 所在网络访问；Kindle 上的
`localhost` 指 Kindle 自己。云端 HTTPS 免去同一局域网限制，但增加部署维护、
鉴权、费用和书籍文本托管问题。未经授权不开放公网端口。

## 2. 愿意使用 KOReader：优先验证现成插件

[KOReader 官方安装说明](https://github.com/koreader/koreader/wiki/Installation-on-Kindle-devices)
要求 Kindle 已越狱；能否越狱取决于型号、变体和固件。该说明还指出 EPUB 是其
最佳支持格式，KFX 与 DRM 保护书籍不受支持。本项目保留的原始 EPUB 比已发送到
原生书库的转换产物更适合这条路线，不以处理 DRM 作为本次方案的一部分。

[Assistant 插件](https://github.com/omer-faruq/assistant.koplugin)已提供选中文字后的
翻译、解释、自定义 prompt，以及 OpenRouter 和兼容 API 配置；因此无需先从零
开发 Kindle UI。可先尝试“选中 → 帮我读懂 → 短答案 → 关闭回到原文”。

[KOAssistant](https://github.com/zeeyado/koassistant.koplugin)也是候选，提供可配置动作
和自定义兼容端点；其 README 明确跟踪 main 分支，部分功能可能尚未进入发布版。
两者都只是已查证存在的候选，没有在本项目设备上安装、审计或验证 GLM Flash。
接入仍需核对实际 endpoint、模型名、思考参数、响应格式和流式行为。

插件可经 Wi-Fi 直接访问远程模型 API，不必始终开着电脑。可选代理用于隔离主密钥、
统一 prompt 或复用本项目缓存；如果直连已满足需要，不为实时功能强行增加服务器。
直连意味着凭据保存在设备配置中，应使用可撤销且有费用限制的专用凭据。
[KOReader 用户指南](https://koreader.rocks/user_guide/)明确提醒，外部插件未经其开发者检查。

当前 [Kindle Modding](https://kindlemodding.org/)已有近期更新的方案，不能沿用旧资料
断言“12 代一定不能越狱”，也不能仅凭代际断言一定支持。先确认固件；不因研究而
升级、降级或执行越狱。该选择涉及设备维护，需用户另行决定。

## 3. Amazon 自带 AI 不等于可接入自己的模型

本次找到的 Amazon 官方说明于 2026-07-02 更新：Ask this Book 当时提供给美国的
Kindle iOS 用户，设备端和 Android 计划稍后扩展；覆盖部分购买或借阅的英文书。
该页面没有提供个人侧载 EPUB 或自选 GLM 的开放接口。因此，截至本次查证，不能
把 Paperwhite 上可用的自定义模型能力当作既成事实。不要把已经上设备的 Recaps /
Story So Far 与 Ask this Book 混为一谈。参见
[Amazon 功能说明](https://www.aboutamazon.com/news/books-and-authors/kindle-recaps-feature-ebook-series-refreshers)。

## 4. 对阅读辅助改造的影响

实时选区调用的价值是由读者指出实际卡点，减少模型事先猜测难点；代价是每次卡住
都要承担联网等待。这是设计判断，并非“实时一定更利于语言学习”的研究结论。

建议在线动作起步只保留“帮我读懂”和可选“翻译”。同一个解释动作按需要给出
短语释义、句意或指向原文的表达提示，不要求每次填满三层结构，不附练习。
解释不够时由读者追问或请求翻译；不默认执行两阶段调用来增加每次等待。

可以复用项目模型客户端、prompt 中的阅读目标、原文身份和诊断思路；不应直接将
整段离线生成契约当作每次在线回答的硬要求。当前工作树已有实验性的
`generate_reading_assistance` 与 `ParagraphAssistance`，但它们并不等于已具备
网络服务、设备集成或可靠缓存；本研究不改动这些正在进行的实现。

离线与在线有三个可比较的使用方式：仅离线、仅按需在线、离线基础辅助加在线补漏。
先比较真实阅读中断，再决定是否替代或保留离线生成，不为支持实时而立即重做整个工具。

## 5. 最小验证顺序与验收

1. **确定设备条件。** 记录确切型号/变体、固件和是否越狱；无需提供完整序列号。
2. **不越狱路线先测交互。** 用数段自有测试文本和固定假答案，走实际导入方式，验证
   外链、中文显示、返回同一段、断网、休眠恢复。先不接模型、不上传真实书籍。
3. **KOReader 路线先测现成插件。** 仅在用户决定采用且设备满足条件后安装；关闭
   自动摘要、练习、自动选区调用及不必要的整书上下文，避免普通选中就触发费用。
4. **通过交互后再测 GLM。** 经授权做小样本调用，核对选区/段落内容、有限语境、
   提示质量、费用、错误恢复，以及实际供应商参数兼容性。

初步技术验收：至少十次取文→查看答案→返回原位置均成功；无串段、正文改写或
凭据泄露；断网可退出回书；浏览器连点和刷新不重复生成同一任务。插件缓存和重试
行为同样要查证，不能把“有聊天记录”当作“重复请求不扣费”。

记录首个可用答案时间、完整答案时间、回到原文操作数、冷启动/恢复联网时间，
以及一段连续阅读中的中断感；同时对照现有离线章末辅助。不预报未经测量的秒数、
续航损失或费用。若固定假答案的浏览器往返已经难以接受，就停止该路线的服务开发。

**建议：保留原生系统时先做浏览器往返验证；愿意换阅读器且固件允许时优先试现成
KOReader 插件。当前最需要补齐的信息是固件版本及是否已越狱，而不是再设计一套
复杂的生成流水线。**
